# Local practice latency model

The Settings window exposes **Simulated Ping (RTT, ms)**. Default 0 means off. The 50 ms input steps provide 0/50/100/150/200 ms choices; any integer from 0 to 300 ms is accepted and persisted. Changes take effect on the next local run/restart, avoiding mid-run history or action ordering changes.

This is an estimated outgoing transport model for more realistic timing pressure. At 150 ms RTT the simulated server receives movement and successful actions approximately **75 ms** later. The encounter timeline is unchanged. There is no incoming presentation delay and no jitter. The supplied captures cannot establish the time at which the actual server received each player's outgoing movement, so RTT/2 is a modeling assumption, not a measured FFXIV protocol constant.

## Architecture and behavior

* `PlayerMotion` continues reading the native model and sending existing local steering/forced movement normally. It never consults delayed positions. `Game.Tick` samples the native player's scenario-local position and facing before encounter events execute. `LocalLatency` retains timestamped samples using unpaused real frame time, independently of encounter speed. Mechanics read the most recent sample at or before `now - RTT/2`, through `SimPlayer`'s mechanic pose. Samples are held rather than interpolated: a native warp never invents a traversed path. This incurs up to one sampled frame of extra quantization. Existing mechanic-specific target locks or stored snapshots use that server view once, with their existing later impact timing unchanged.
* Both position and facing are delayed for geometry, tower checks, target selection, proximity, and mechanic snapshots. The player's actual model and controls remain immediate. Server-authoritative `SetPosition`/`TeleportTo`, including Return/Rewind, discard older movement history because the server already knows those destinations. Knockbacks, carries and slides retain native movement and subsequent reports; their physical animation is unchanged. Native fall detection still observes the physical player.
* Native `LocalPlayerInputHooks` emits `ActionExecuted` after the client's actual execution, rather than each queued/spammed button press. `UserActions` retains the existing `LastUsedActionSequence` deduplication and the native client's queue/recast/GCD behavior. Instant-action resolved effects, including Provoke and defensive abilities, are scheduled on the existing encounter scheduler after outgoing RTT/2. Hard casts still start and interrupt on the existing native pipeline; only a successful completion's effects are delayed, once. This approximates receipt of a completed action, without attempting to recreate server cast acceptance or its prediction protocol.
* The queued closure captures action type, action ID and target ID. Ordered scheduler insertion preserves equal-time order; a later target change does not retarget a submitted Provoke. Eligibility is checked again at receipt where the existing action handler requires it. Dead players cannot resolve delayed actions. Local practice invulnerability/anti-knockback substitute buttons reserve their once-per-run use on press, activating after the same delay.
* `TankSwapSequence` and scenario listeners receive Provoke through their existing `ActionResolved` event after acceptance. Existing mitigation/status and damage snapshot rules remain responsible for whether an accepted effect protects a hit. Bots' action and movement paths do not enter this queue.
* Delay is converted to encounter seconds when an effect is submitted. At a constant encounter-speed setting it remains RTT/2 of unpaused real time. Changing speed while an action is in flight can change its remaining wall-clock delay; use a fixed speed when comparing deadlines. Scheduler events and geometry retain the engine's existing frame quantization. A submitted action exactly equal to an already-scheduled mechanic's deadline executes after that mechanic.

## Lifecycle and modes

Only **local** human practice enables this model, in both inn and title-screen offline sessions. These entry paths share the same native input boundary and `Game`/`SimWorld` pipeline. Host/peer multiplayer is excluded; adding per-participant transport delay would need a separate model to avoid compounding its real relay transport. JESUS TAKE THE WHEEL has eight bots and uses zero simulated latency. Normal practice retains seven unaffected bots.

Pause freezes both the history clock and acceptance scheduler. Pause restoration uses the immediate local native pose, so pausing cannot move the model backward to a historical position. Restart and scenario transitions clear history and pending scheduler entries, then seed the new run from its placed player. Leave clears the model immediately. A delayed practice substitute callback is also guarded by its activation generation so it cannot cross a reset. Zero RTT calls effects synchronously and reads the immediate pose, retaining the pre-feature path.

Acceptance entries share the existing event scheduler; a last input may keep its completion detector nonempty for at most one one-way delay. This does not shift any encounter event. Local auto-attacks, the client's own cast bar, GCD/recasts and animation lock are not delayed. Job action confirmation/status feedback occurs with resolved effects; there is no additional incoming half-trip. The existing optional local-action setting still controls job handlers.

## What this does not reproduce

This does not reproduce actual server tick scheduling, packet emission cadence, packet loss/retransmission, proprietary movement prediction, cast acceptance or slidecasting adjustments, RTT-dependent animation-lock behavior, congestion, asymmetric paths, or exact client/server clock synchronization. A 150 ms setting is not a promise of exact retail behavior at 150 ms measured ping.

The feature neither intercepts nor delays real network packets. It changes local sim state and schedules existing local action handlers only. It does not change firewall entry guards, packet opcodes, native actor scheduling, cast lengths, VFX/omen timing, server connection configuration, or restoration ownership.

## Validation and native acceptance

`LocalLatencyTests` covers movement departures before/near/after a snapshot at 0/100/150 ms, actual historical sample/facing selection, warp reset, RTT/2 action receipt and ordering, mitigation deadlines, pause/reset cancellation, persisted bounds, immediate native movement versus delayed mechanic pose, and actual native-action-hook sequence deduplication and delayed mitigation dispatch.

Debug validation on October 25, 2026: 39 latency cases plus 62 existing action/defensive/spectator regressions passed (101 total, 9 seconds NUnit duration; 10.798 seconds measured command wall time). The direct test-project Debug build succeeded with 0 errors in 11.13 seconds (11.326 seconds measured wall time); existing platform annotations and package vulnerability-source warnings remain. Integrated solution and packet safety validation are reported by the shared integration workstream.

Still requires in-client acceptance in both inn and offline: immediate walking/turning, borderline dodge failure without visual rubberbanding, hotbar queue/recast behavior, hardcast interruption and resolution, Provoke on a changing target, mitigation before/after a real simulated tankbuster, forced-movement/Return visuals, pause after recent movement, restart/leave while effects are pending, and spectator switching. Headless tests cannot validate native rendering or prove real RTT equivalence.
